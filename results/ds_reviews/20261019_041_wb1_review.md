# 理论背景（Why）

CEO 在阿里云 PAI-DSW 用手机浏览器操作终端：多行粘贴会卡死，断网会中断任务。
DS 提出两条路径：

1. **一行入口**：把 wget→解压→环境变量→pip→运行压成一条极短命令；
2. **后台运行 + 自动回传**：`nohup` 挂起，跑完把产物推回 GitHub。

DS 同时明确边界：WB 无法直接 SSH 进 CEO 的实例（无公网 IP、无凭据、无法控制手机）。
这个判断是对的。

# 具体步骤（What）

1. 写一个仓库内的入口脚本，用户只粘一行；
2. 支持后台模式，关掉手机不中断；
3. 可选：跑完自动把产物推回 GitHub。

# 验收标准（How）

- 一行命令在无 GPU 环境（SMOKE）下能跑通；
- 后台模式能返回 PID，且进程结束后产物完整；
- 下载环节在「raw 被墙」时仍能成功。

> 本评审不含新假设（运维易用性改进），台账不新增条目。

## 反直觉与异常观测

### 1. DS 给的 raw 链接在我的沙盒里**直接超时**，但在 DS 的推演里是「能下」

这不是 DS 的错——它无法实测。但它意味着：**任何「一行 curl」方案如果只写 raw，
在国内环境有相当概率第一条命令就卡死**，而 CEO 只会看到光标不动。

### 2. CDN 的「包已更新、入口脚本仍旧」是最阴的失败模式

jsDelivr 上 tarball 已刷新（49091），但 `bootstrap.sh` 仍返回旧版（期望 48618）。
若用户此刻跑 jsDelivr 的一行命令，旧脚本会拿 48618 去校验 49091 的包 →
**必然判失败**，而错误信息看起来像「下载坏了」，实际是版本错位。

处置：① 主入口改用 `ghfast.top`（直通 raw，无 CDN 缓存滞后）；
② 增加**版本漂移兜底**——严格哈希全失败后，若包是合法 gzip 且含
`deploy_autodl/run_all.sh`，则打印期望/实际 sha 并继续；`STRICT_VERIFY=1` 可拒绝。

### 3. 打包脚本会改 README，README 又在包里 → 哈希自我变化

`build_deploy_bundle.sh` 把 README 打进包，所以「改一句文档」也会让 sha 变。
若不联动 bootstrap 的 `EXPECT_SHA`，每次改文档都会让用户下不了包。
已在打包脚本末尾加自动同步（避免人肉记哈希）。

### 4. 后台任务的「成功」必须看退出码，不能看进程消失

第一次后台测试，进程没了、日志也有输出，但 `results/` 里少一个文件——
因为 Step 5 早退而脚本当时还 `exit 0`。已改为累计 `FAILED` 并传递退出码。

## 结论

1. 一行入口 + 后台运行已交付并实测（26s / exit=0 / 产物齐全）。
2. 下载改为三镜像回退 + 逐镜像哈希校验 + 版本漂移兜底；raw 被墙不再是阻塞。
3. 自动回传代码就绪但未实测（需 CEO 的 token），默认关闭。
4. 打包脚本与 bootstrap 校验值已自动联动，消除人肉维护。
