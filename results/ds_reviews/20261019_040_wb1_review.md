# 理论背景（Why）

CEO 在阿里云手机端执行遇到硬阻塞：终端卡死、网络断连；且 7B 对部署环境要求过高
（显存、下载量、单次跑批时间）。DS 据此做战略调整：

- **目标模型正式降级为 `Qwen/Qwen2.5-3B-Instruct`**；
- 理由：3B 与 7B **同构**（同样有 GQA 与相同注意力机制），但 `hidden_size=2048`，
  显存与下载成本大幅下降，能在低算力环境稳定产出真实数据。

这是**用模型规模换可执行性**的取舍：牺牲一部分表征容量，换取「真的能跑完」。

# 具体步骤（What）

1. **环境守卫更新**：`model_is_7b` → `model_size_in_3b_7b`（接受 3B 或 7B）；
   维度期望支持 2048。
2. **默认模型改 3B**。
3. **提供新的手机端单行命令**（减少粘贴量）。

# 验收标准（How）

- 产出 `kaggle_3b_fixed_route.json`，四条环境断言通过；
- 产出 `real_features_3b.npz`，维度严格 `(N, 2048)`。

## 反直觉与异常观测

### 1. 改一个数字（3584→2048）牵出 5 处耦合

`hidden_size` 不只是断言里的常量，它还决定：默认模型、`--expect-dim` 的默认值、
产物文件名、环境标签（`*-3b`）、README 的验收表。
只改断言会让后面四处全部错位——**「改个常数」从来不是只改一个地方**。
故改为**按模型名推断规模**（`3B/7B` → `SIZE_DIMS`），一处定义、五处派生。

### 2. `Path.with_suffix()` 把 `.5b` 当成文件后缀，产物名被吃掉

SMOKE 模式产出 `real_features_0.npz` 而不是 `real_features_0.5b.npz`：
`Path("real_features_0.5b").with_suffix(".npz")` 会把 `.5b` 判为后缀并替换。
这不是 3B 引入的 bug，而是被「带点的规模标签」触发的**潜伏 bug**。
已改为字符串拼接，并容忍用户显式传 `.npz/.json`。

### 3. 3B 的「同构」是假设，不是已验证事实

DS 说 3B 与 7B 同构（GQA + 同注意力机制），这在 Qwen2.5 家族内基本成立，
但**表征容量差 ~2.4 倍**（2048 vs 3584 维）。H-DS37 就是为这个留的证伪口：
若 3B 特征训出的路由连随机线都过不了，降级就是失败的，必须回 7B。
**不能因为「跑得动」就默认「够用」。**

## 结论

1. 守卫、默认值、产物命名、文档已全部切到 3B，7B 保持兼容（10/10 单测）。
2. 手机端一行命令不变，默认即 3B；产物自动命名 `*_3b`。
3. 3B 是否足够训练路由，交由 H-DS37 用真实重训结果裁决。
4. 待 CEO 在云上跑出 `real_features_3b.npz`（`(N,2048)`）与 `kaggle_3b_fixed_route.json`。
