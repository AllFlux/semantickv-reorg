# 理论背景（Why）

CEO 决定停止外部云平台（阿里云验证码、计费、断连风险），把执行搬回本沙盒。
DS 的判断依据是「沙盒内存足够（3B 4-bit 仅需约 2GB）」，据此要求在沙盒内直接跑
真实 3B 推理，完成全自动闭环。

这条判断的方向完全正确——本机确实有能力跑：`free -h` 实测 **123Gi 总量 / 92Gi 可用**、
32 核 AMD EPYC 9K65、252G 磁盘。但其中「4-bit 只需 2GB」这一条**在 CPU 上不成立**，
详见下文实测。

# 具体步骤（What）

1. 环境侦察：内存 / CPU / 磁盘 / bitsandbytes / HF 可达性。
2. 沙盒内直接跑 3B：`fixed_route_assault.py`（Step 5）与 `export_real_features.py`（Step 6）。
3. 产出 `kaggle_3b_fixed_route.json` 与 `real_features_3b.npz`。

# 验收标准（How）

## 反直觉与异常观测

### 1. `--load-in-4bit --device cpu` 在 CPU 上根本不成立

DS 的原命令含 `--load-in-4bit --device cpu`。实测：bnb 0.50.2 的 4bit（NF4）后端是
**CUDA kernel**；CPU 路径要现场从 `kernels-community/quantization-bitsandbytes`
拉预编译 kernel，而这一步需要 `trust_remote_code=True` 且信任校验：

```text
Failed to load CPU gemm_4bit_forward from kernels-community:
  Kernel repository 'kernels-community/quantization-bitsandbytes'
  could not verify publisher trust status.
FP4 quantization state not initialized. Please call .cuda() or .to(device) ...
AssertionError
```

**更关键的是：这里根本不需要 4bit。** 4bit 是为了省显存；本机是 123GB 内存，
3B 的 bf16 权重只有 6.2GB。**为了省一个不存在的约束，去引入一个会失败的依赖**，
是典型的「把 GPU 经验错套到 CPU」。

而且 bf16 比 4bit **更真实**：NF4 量化会引入权重误差，而我们的目的恰恰是导出
「真实分布」给 WB2 重训。用 4bit 反而是自相矛盾。

### 2. 为跑 4bit 装的 `kernels` 包，会毒化整个 transformers

按 bnb 的提示 `pip install kernels>=0.11.1` 后，transformers 5.1.0 直接不可用：

```text
File ".../transformers/integrations/hub_kernels.py", line 88, in <module>
    "cuda": LayerRepository(
File ".../kernels/layer/layer.py", line 117, in __init__
    raise ValueError("Either a revision or a version must be specified.")
```

`hub_kernels` 在 **import 期**就构造 `LayerRepository`，而新版本 `kernels` 要求必须给
revision/version —— 两者不兼容。**整个 `AutoModelForCausalLM` 都 import 不了**，
不只是 4bit 路径。卸载 `kernels` 后立即恢复。

> 教训：一个"可选加速包"能在 import 阶段拖垮主栈。装它之前应当先问「我到底需不需要它」。

### 3. bf16 张量不能直接 `.numpy()`——三处潜伏 bug 只有换 dtype 才暴露

numpy 没有 bfloat16 dtype：

```text
TypeError: Got unsupported ScalarType BFloat16
```

原来只跑过 float32 / float16，这条路径从未被踩。切到 bf16 后连爆三处：

| 位置 | 用途 |
|---|---|
| `hidden_from_capture()` | 导出隐状态（主路径） |
| `CompressedAttentionPatcher.fwd` 内的 `imp[0,h].numpy()` | TopK 选择（每层每 KV 头） |
| `select_topk_per_group` 调用点 | 分组内 TopK |

统一改为先 `.float()` 再 `.numpy()`（对 fp32 是 no-op）。这不是"3B 的问题"，
是**任何 bf16 推理都会踩的通用坑**。

### 4. 3B 的压缩保真度**低于** 0.5B，但任务全对

对比两次实测（同一套混合保护配置）：

| 模型 | gsc 路由 cos 均值 | needle 命中 |
|---|---|---|
| Qwen2.5-0.5B（CPU/fp32 代理） | **0.806** | 3/3 |
| Qwen2.5-3B（CPU/bf16 真实） | **0.686** | 3/3 |

直觉上"模型越大越鲁棒"，cos 应该更高。实际相反：**大模型的 cos 更低，但答得一样对**。

合理解释：3B 的表征更各向异性、方向更"锐利"，压缩重组造成的方向偏移在余弦上更明显；
但语义冗余度也更高，所以即使 cos 掉到 0.69，答案仍然正确。

> **这条直接否定了「用 cos 阈值当验收线」的做法**。cos 只能当"压缩强度"的读数，
> 不能当"是否还能完成任务"的判据——真正的判据是 needle 命中。

### 5. 第一次导出的特征被偷偷归一化了（范数恰好 1.000）

首版 `real_features_3b.npz` 的 L2 范数均值正好 `1.000`、标准差 `0.000`。
原因：`smooth_hidden()` 默认 `renormalize=True`，而它同时用于"聚类"和"导出"。

若把这个交给 WB2，会出现**训练-推理分布偏移**：训练时输入单位向量，
推理时喂给 Router 的是原始幅值（范数 130 量级）→ Router 直接失效。
已改为：**平滑 + 归一化只作用于聚类输入，导出的是 `H_raw` 原始幅值**。
修正后范数为 78.8–228.2（均值 132.4），并在 meta 里显式声明
`raw_hidden_exported=true / l2_normalized=false`。

## 结论

1. **沙盒闭环成立**：真实 3B 模型在本机跑通，两份产物均已产出。
2. **Step 5**：`kaggle_3b_fixed_route.json`，baseline 1.000 门禁 PASS，
   三路由 Argmax 全 **1.000**、无 ROPE 崩塌 → **verdict=MAINTAIN**。
3. **Step 6**：`real_features_3b.npz`，`(2586, 2048)`、42 群、原始幅值、无 NaN/Inf。
4. **DS 指令的一处修正**：`--load-in-4bit --device cpu` 不成立，改用 bf16 全精度
   （内存充裕，且更保真）。
5. **诚实边界**：设备是 CPU（非 GPU）、无 4bit 量化、序列 2586 token（非满 8K）。
   模型规模与维度（3B / 2048）是真实的，与之前的 0.5B 代理有本质区别。
