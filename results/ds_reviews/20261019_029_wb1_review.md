# 理论背景（Why）

DS-029 是对 R18 交付的三点裁决：

1. **批准 MAINTAIN**。0.5B CPU 代理下 1.000 证明「管线 / RoPE 连续性 / 混合保护」
   逻辑自洽，DS 正式认可该判定。
2. **push 被拒未 force** 被评为「卓越的工程素养」——若当时 `--force`，WB2 的 7 个
   提交与新权重会被永久覆盖。DS 把「永不 force push 共享仓库」定为军规。
3. **GAP-DS26-01（1024 vs 3584）复核精准**。DS 已勒令 WB2 按 3584 重训；
   WB1「维持封存 wb2_router」被明确肯定——**不要在错误维度上浪费时间**。

DS 同时给出一条重要判断：**0.5B 数据已完全饱和**（3/3 全中，GSC 与 qk 无法区分），
继续在 0.5B 上调参毫无信息量。唯一有价值的动作是把同一脚本搬上 7B。

# 具体步骤（What）

1. **Kaggle 7B Run All（Step 5）**：加载 `Qwen2.5-7B-Instruct`（4bit，8K），
   产出权威 `kaggle_7b_fixed_route.json`。
2. **导出真实特征**：7B Prefill 阶段的 `Query_Hidden_State`（3584 维）+
   真实 GSC 分组标签 → `.npz`/`.json`，交给 WB2 打破「合成数据自证」的循环论证。
3. **回传与审计**：7B Argmax ≥45% 交数据；若仍 1.000（needle 过易）→ 改用
   **KVFundaBench 推理密集型子集**；若 <45% → 标记 `ROPE_FRACTURE` 转查位置编码。

# 验收标准（How）

  且**不得把代理环境冒称为 7B**。
- 输出真实 7B Argmax 数值 + 3584 维隐状态样本导出包。

## 反直觉与异常观测

### 1. 「0.5B 全中」其实是坏消息，不是好消息

三种路由 Argmax 全 1.000、needle 全 3/3，直觉上像"方案大成功"。但 GSC 分 14 群、
qk 只分 2 群，两者差异巨大，结果却完全相同——说明**任务难度低于模型能力，
指标已经饱和**。DS 的判断（"0.5B 数据已完全饱和，继续跑毫无意义"）与观测一致。
教训：**指标全满时先怀疑任务太简单，而不是庆祝**。

### 2. 特征导出最容易错的地方是「维度悄悄不对」

`hidden_from_capture` 返回的是 `(N, hidden_size)`，0.5B 是 896、7B 是 3584，
代码路径完全相同。若不显式核对 `hidden.shape[1] == config.hidden_size`，
就可能导出一份"看起来正常、维度却错"的文件，WB2 拿去重训会再次踩 GAP-DS26-01。
故脚本在落盘前强制断言，并把真实维度写进 meta。

### 3. 环境标签是唯一能防止「假 7B 结论」的闸门

`--environment kaggle-7b` 是一个**人可以随手打上的字符串**。若不加守卫，
任何人（包括未来的我）都能在 CPU 上跑 0.5B 然后把结果标成 7B 权威数据——
这正是 D3 要防的事。故把标签从「注释」升级为「需通过四条断言才允许写入」。
