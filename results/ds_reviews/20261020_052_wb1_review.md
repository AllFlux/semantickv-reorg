## 理论背景与肯定（Why）

DS-052 首先确认上一轮（DS-051）三项机制化验收通过：路径强制、内联哈希、分卷机制全部落地；并肯定 WB1 找出的「8.2MB 实为 7.84MB」与 `src/src/shared` 双目录 bug 修复及时，分卷设计有效规避了 CDN 单点故障。

本轮的真正硬点是 **D-65a 的命名冲突**：DS-051 要求把哈希字段写成 `sha256`/`byte_size`，而 DS-052 现在明确 `real_features_3b.json` 的 **`export_sha256` 才是唯一真值**，WB2 的 `validate_wb2_input.py` 信任并读取它。若 json 只有 `sha256` 而无 `export_sha256`，WB2 校验器将依法拦截。因此必须把字段名收敛为以 `export_sha256` 为唯一真值，同时不破坏 DS-051 的 `sha256` 别名要求。

## 具体步骤（What）

1. **字段收敛**：在 `export_real_features.py` 中，哈希**只计算一次**，镜像写入 `export_sha256`（唯一真值）与 `sha256`（DS-051 别名），`byte_size` 同理镜像 `export_byte_size`；根 `meta` 与内层 `meta["meta"]` 双写。二者恒等，杜绝「两份真值不一致」这一 D-65a 要防的根因。
2. **校验器优先读唯一真值**：`tools/validate_wb1_export.py` 的 `read_expected_sha` 改为**优先读 `export_sha256`**（回退 `sha256` 别名）；`--write` 同步镜像写这两个键。
3. **同步现有交付件**：对既有 `src/shared/real_features_3b.npz` 跑 `--write`，把 `export_sha256=84e37106…e5b261`、`export_byte_size=8215605` 补写进 json（npz 未改动，故哈希不变）。
4. **文档固化**：`src/shared/README.md` 新增 §9.2，写明 `export_sha256` 唯一真值、别名恒等约定、以及「重新生成 npz 必须同步更新 json」的强制要求。
5. **维持冻结**：`version_freeze=true` 延续，仅做上述机制化修补。

**反直觉与异常观测（D3-b）**：

1. **DS-051 与 DS-052 的字段名冲突本身是风险**：上游两次指令分别要求 `sha256` 与 `export_sha256`，若机械二选一会破坏另一方的校验链。解法是「一次计算、双键镜像、值恒等」——既满足 DS-051 的字面字段，又满足 DS-052 的唯一真值，且从机制上杜绝两份哈希漂移。
2. **「唯一真值」不等于「只准一个键」**：D-65a 的核心是「只有一个权威哈希值」，而非 JSON 只能有一个键。两个键指向同一计算值，仍是单一真值；反之若让两个键各自独立计算，才真正违背唯一真值。
3. **集成测试尚缺最后拼图**：DS-052 §三 的端到端集成测试（挂载最终 Router 权重后确认 Argmax 及格）需等 WB2 push **input_dim=2048** 版最终权重；`fetch` 确认远端 `origin/main` 仍停在 `5836772`，`src/shared/semantic_router.pt` 仍是旧版，故本轮不跑集成测试，只把交付链路（导出 + 校验 + 分卷 + 唯一真值）彻底闭合待命。
